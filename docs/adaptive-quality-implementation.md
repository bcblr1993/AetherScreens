# Adaptive display quality implementation

Current source audit (2026-10-09): DisplayQualitySettingsView exposes only fullColor/rgb565. SessionViewModel.selectDisplayColorDepth disconnects and reconnects. RFBClient.setupSession advertises ZRLE/Zlib/CopyRect/Raw and supported pseudo-encodings, not Tight. None of these proves adaptive compression.

Primary protocol: https://github.com/rfbproto/rfbproto/blob/master/rfbproto.rst (encodings and JPEG-quality pseudo-encoding). Tight pixel encoding is 7; ZRLE is 16. Tight security authentication type 16 is a separate namespace and must not be confused with pixel encodings. JPEG quality levels -32 through -23 are server hints, not bandwidth guarantees. The current implementation must not advertise Tight until it can decode all required subencodings, filters, stream resets and lengths. Adding only a JPEG branch is insufficient.

Required implementation sequence:

1. Bounded Tight reader and decoder: compact lengths, fill, JPEG through ImageIO, basic compression with four independent persistent zlib streams, copy/palette/gradient filters, strict rectangle and decoded-byte bounds. Cover malformed/truncated input, palette edge cases, stream resets, and fragmented actual TCP frames. Only then advertise the format.
2. Explicit quality mode stored per computer, with existing manual color preference preserved. Automatic compression adaptation must avoid repeated reconnects and must not imply scaling or HEVC support.
3. Adaptation samples must distinguish an idle desktop from congestion. Use actual outstanding-frame timing, transport samples and measured bytes; apply hysteresis, minimum sample counts and cooldowns. Ignore stale generation callbacks and hidden sessions. Low FPS on an unchanged desktop is not a downgrade signal.
4. Update encoding/quality hints on the serialized transport boundary, retain fallbacks and verify decoded frames while hints change. A server may ignore the hint; display effective behavior truthfully.
5. Validate a controlled changing-network server with received packet evidence, image correctness and measured responsiveness, then the authorized Mac mini with actual chosen encoding. Native Apple display configuration is a separate path and must be inspected rather than presumed to support Tight.
6. Physical iPhone acceptance remains required for motion, text clarity, typing/pointer latency and energy/hitch behavior. Core tests and synthetic measurements cannot close that gate.

No adaptive mode has been enabled by this audit. No new production dependency, deployment or remote setting change was made.

Release intent (user request, 2026-10-09): after completing this phase, publish a new version if the candidate meets the release gates. This authorizes the scoped app release workflow; it does not make incomplete decoding or unverified device behavior accepted. Before publication, finish the decoder and adaptive mode, validate the final installed candidate, synchronize remote version metadata without overwriting this dirty checkout, pass CI, sign/notarize and inspect the DMG, then verify public assets and website downloads. Current distribution remains macOS; iOS publication requires its own Apple distribution setup and acceptance.

Implementation checkpoint (2026-10-09): Tight length, pixel conversion/fill, palette, gradient, four persistent streams, JPEG and side-effect-free rectangle framing are implemented. RFBClient reads bounded headers and complete payloads, then decodes on its serial worker with connection identity guards. The final image ceiling is 256 MiB. Standard RFB now advertises Tight while retaining ZRLE/Zlib/Raw. Native Apple configuration remains unchanged. Automatic compression is implemented as an opt-in per-computer preference and is under integration acceptance.
